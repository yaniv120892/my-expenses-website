# Worked examples

Three real PR bodies from this repository, reproduced verbatim, each with a
note on what it is doing structurally. Read the note, then read the body and
watch the note happen.

The point is not to copy these section names. It is to see how much of each
body is reasoning the diff could never supply, and how little of it is a
summary of the diff.


## Example 1 — a small fix (~2,000 characters)

Four short sections. What makes it work is the second one: the bug is not
reachable in production today, so instead of overselling it the description
says exactly that in a heading and then argues why it is still worth fixing.
That is the honest move, and it is more persuasive than a fake severity
claim would be. Note also that the opening sentence gives the bug's origin —
an audit — rather than jumping straight to the symptom.

**Title:** `Acknowledge announcements in batches the route accepts`

<details>
<summary>Full body</summary>

Third of three fixes from the client/schema mismatch audit that followed #39. This one is **latent, not live** — worth fixing cheaply now rather than debugging later.

## The bug

`acknowledgeAnnouncementsSchema` caps a request at 50 ids:

```ts
ids: z.array(z.string().min(1)).min(1).max(50)
```

`WhatsNewAutoDialog` acknowledges every unseen announcement in a single call with no chunking:

```ts
acknowledge(unseen.map((announcement) => announcement.id));
```

Past 50 unseen, that request 400s. Reproduced: 51 ids → `{"code":"too_big","maximum":50,...}`.

## Why it matters despite being unreachable today

Only one announcement ships in `src/shared/announcements.ts`, so nothing breaks right now — it starts failing at the 51st, and it fails **silently**. The dialog closes optimistically and the write is deliberately fire-and-forget:

> Closed optimistically and the write runs in the background: trapping the user behind a failed request would be worse than showing this again.

That's the right call for a transient failure, but it means a systematic 400 surfaces as "What's new" reappearing on every single load, forever, with nothing in the UI pointing at the cause.

## The fix

The client splits the ids into consecutive requests of at most `MAX_ACKNOWLEDGE_IDS` and merges the results. The schema exports that constant so both sides read the same bound rather than repeating the literal — the same single-source principle as the sibling PR on the trends bound.

An empty set now sends no request at all, where before it would have tripped the schema's `min(1)`. `WhatsNewLauncher` already guarded that case; `WhatsNewAutoDialog` relied on the dialog's open condition to do it implicitly.

## Verification

- New tests cover the single-request case, the oversized split (every batch re-parsed with the real schema), and the empty case.
- `npm test` — 113 passed.
- `npm run typecheck` and `npm run lint` clean.

## Example 2 — a fix with a defended alternative (~2,400 characters)

The centrepiece is `## A note on the alternative`. There was a smaller diff
available; it is named, its consequence is spelled out (a silent no-op that
Prisma's `undefined` semantics would hide), and the reason it was rejected is
a product judgement rather than a technical one — so the author says so and
offers to switch. A reviewer can overrule the decision in one comment
instead of discovering it in the diff.

Also worth copying: the two schema snippets set side by side with a `←`
pointing at the disagreement, and the real validation error pasted in. The
`Verification` block is three lines, because the change is small.

**Title:** `Require a category when editing a transaction`

<details>
<summary>Full body</summary>

Second of three fixes from the client/schema mismatch audit that followed #39.

## The bug

The two transaction schemas disagree about the category, and `TransactionForm` treats both modes the same:

```ts
// createTransactionSchema
categoryId: z.string().uuid().optional()
// updateTransactionSchema
categoryId: z.string().uuid()            // ← required
```

`handleSubmit` maps an empty category to `undefined`, and `validate()` never required one. `CategorySelect` is a MUI `Autocomplete` with no `disableClearable`, so it has a clear button — and the form actively invites using it with *"If category is not filled, it will be generated by AI"*, a hint that rendered while editing too.

Clearing the category on an edit therefore sent `categoryId: undefined` and the PUT failed validation:

```
[{ "code":"invalid_type", "received":"undefined", "path":["categoryId"], "message":"Required" }]
```

Same asymmetry as #39: creating without a category works, editing to remove one 400s.

## The fix

The form now requires a category when editing — matching what `ScheduledTransactionForm` already does for the same required-uuid constraint — and the AI hint is limited to creates, the only mode where the server actually fills a missing category in.

Validation moved to a pure helper so the create/edit rule is testable under the node-env vitest setup. The test also parses the payloads the form builds against the real API schemas, so the form rule and the route contract can't drift apart again.

## A note on the alternative

`transactionService.updateTransaction` already takes `CreateTransactionRequest` (where `categoryId` is optional) and guards `if (data.categoryId)`, so the service tolerates an absent category — only the schema rejects it.

Relaxing the schema instead would be a smaller diff, but it would make clearing a category a **silent no-op**: Prisma reads `undefined` as "leave unchanged", so the old category would survive while the UI implied AI had picked a new one. Making that gesture actually re-run AI categorization is a product decision and real feature work, so this PR keeps the API contract as-is and makes the client honest about it. Happy to switch if you'd rather have the endpoint accept clearing.

## Verification

- `npm test` — 115 passed.
- `npm run typecheck` and `npm run lint` clean.

## Example 3 — a large feature (~6,200 characters)

Section names are the feature's outline, not generic labels. The opening
paragraph describes the current experience as a sequence of physical steps
("open the dialog, drop one file, wait…") so the cost is felt before any
solution is proposed, and then notes that the data model already supported
the change — only the client did not. That framing tells the reviewer where
to expect the diff to be.

`## Concurrency hardening` is the part that earns the length: making
extractions parallel promoted latent single-import races into likely ones,
and each race is described as a causal chain, with the specific reason a
compatibility fallback is safe to delete later. `## Known follow-up, not in
this PR` fences the scope explicitly so the omission reads as a decision
rather than an oversight.

**Title:** `Import several statement files in one pass`

<details>
<summary>Full body</summary>

Someone with four credit cards runs the entire Imports flow four times today: open the dialog, drop one file, wait for the upload and the extraction submit, let the dialog close, reopen it, repeat. The dropzone was capped at one file and started the request on drop, which is also why the payment month had to be typed *before* dropping.

Uploading a file already created exactly one import — `importService.processImport` creates one `Import` row per call — so the model was right, only the client was single-file.

## What changed

**Queue instead of upload-on-drop.** Files are queued as rows, each with its own payment month (plus an "Apply to all" for the usual same-billing-month case), and an explicit "Upload N files" starts the batch. Two upload at a time: sequential is as slow as today, and unbounded splits one uplink N ways against a **120s wall-clock** upload timeout, turning a slow batch into N failures. Each row carries its own progress, status and error; a failed row retries without re-sending bytes that already reached S3. The dialog closes only when everything succeeded, and refuses to close mid-batch — unmounting doesn't cancel the in-flight requests, it just hides them.

**Polling.** Four fresh `PROCESSING` rows previously sat there until a manual refresh — there was no `refetchInterval` anywhere in the repo, and the global 60s `staleTime` damps focus refetch. `useImportsQuery` now polls while anything is in flight, bounded by how long *this client* has been watching (so a skewed clock can't disable polling, and a reload starts the window over).

## Concurrency hardening

Running several extractions at once promotes latent single-import races into likely ones:

- **Callbacks resolved only by `excelExtractionRequestId`**, which `submitExtraction` writes *after* the submit returns. A fast callback found nothing, 404'd, and stranded the import in `PROCESSING`. The import id now rides along in the signed webhook URL; the request-id lookup stays as a fallback for callbacks already in flight at deploy time. That fallback is dead an hour after rollout (tokens expire in 60 min) and is marked for removal.
- **Two callbacks for the same card + month could each see the other as the duplicate**, merge into each other, and both hard-delete themselves — the `ImportedTransaction.import` FK is `Restrict`, so at least one hit a violation and left the pair half-merged. Merges now go strictly oldest-wards, and only into an import that is already `COMPLETED` — which it reaches only after writing its own rows, so de-duplicating against it is meaningful. Two callbacks racing therefore both survive as separate imports rather than one silently duplicating every row into the other. The merge's writes go as one `$transaction`.
- **Redelivery.** Each callback claims its extraction first, so a redelivered webhook is a no-op instead of duplicating every row. The claim is deliberately *not* released on failure — the handler isn't idempotent — so a failed attempt is marked `FAILED` and visible, and recovery is delete-and-reimport.
- **`submitExtraction` racing its own callback.** With the signed importId, a callback can complete (or merge away) the import before the submit path finishes. Its `PROCESSING` write is gone (`create` already sets it), and the request-id and failure writes are scoped to an import no callback has claimed — otherwise a successful import could be overwritten as `FAILED`, inviting a duplicate Retry.
- **Matching claimed transactions user-wide with no exclusion set**, so two rows in one import — or in two imports completing together — could take the same transaction. Matching is now sequential over a set seeded from every transaction already claimed.

One migration adds `extractionCompletedAt` and a unique index on `excelExtractionRequestId`. It backfills already-finished imports so a late redelivery can't reprocess them, and detaches duplicate request ids before creating the index.

## Tests

`npm test` is 268 passing, up from 193.

- The per-file pipeline lives in `importUploadRunner`, taking an api object and a dispatch callback, so sequencing, failure isolation and the retry path are covered in plain node. The queue reducer and the concurrency pool are pure modules too.
- This project had no component or hook tests, so **jsdom + React Testing Library** come in with it. The include glob widens to `.tsx` and the two component suites opt into jsdom with a per-file docblock — every other suite stays on the node environment.
- Server-side: interleaved callbacks for the same card, redelivery (including that a failed attempt keeps its claim), both resolution paths, importId tamper rejection, and matching never handing one transaction to two rows.
- **e2e** (`e2e/imports.spec.ts`): a mock extraction agent joins the harness stack and calls the webhook back *after* responding, so the callback races the request-id write — exactly the window the signed importId closes. Only the S3 upload is stubbed, in the browser; everything downstream runs for real, so the spec proves N files become N imports that reach COMPLETED without a reload, and that a rejected file fails alone and retries. Verified locally against `prisma dev`: 13/13 Playwright specs and 46/46 API checks.

Incidental fixes found along the way: the dialog had two fields both labelled "Payment Month (MM/YYYY)" (the batch default is now "Default Payment Month"); the e2e seed never deleted `Import` rows, so its truncate hit an FK violation once anything created one; and the queue cap was only wired to react-dropzone's `maxFiles`, so it bounded one drop rather than the queue — two drops of six gave twelve, and the overflow is now reported rather than silently dropped.

## Known follow-up, not in this PR

Matching went from `Promise.all` to a sequential loop to make the exclusion set meaningful, and it is awaited inside the webhook handler. For a large statement that is N × (DB + one LLM call), which can outlast the serverless timeout. The exclusion set only matters for rows whose ±2-day/±2-value candidate windows overlap, so the fix is to cluster disjoint rows and run those concurrently, or move matching off the response path — a redesign worth its own issue rather than a bolt-on here.

</details>
